# 협업 컨벤션

## 작업 흐름

PR은 커밋마다 생기지 않습니다. **브랜치 하나에 PR 하나**이고, PR을 만든 뒤 같은 브랜치에 푸시한 커밋은 그 PR에 자동으로 추가됩니다.

| 단계         | 할 일                                                                                 |
| ------------ | ------------------------------------------------------------------------------------- |
| 1. 이슈      | `feat`·`fix`는 이슈를 먼저 만듭니다. 나머지 타입은 선택입니다 ([이슈](#이슈) 참고).   |
| 2. 브랜치    | `git switch main && git pull` 후 `git switch -c feat/24-recipe-save`                  |
| 3. 커밋      | `git add .` 후 `git commit -m "feat: 레시피 저장 버튼 추가"`                          |
| 4. 푸시      | 처음: `git push -u origin feat/24-recipe-save` / 두 번째부터: `git push`              |
| 5. PR 만들기 | GitHub 저장소 페이지의 **Compare & pull request** 버튼, 또는 `gh pr create`           |
| 6. 리뷰 반영 | 같은 브랜치에 커밋 후 `git push`. 기존 PR에 추가되고 CI·CodeRabbit이 다시 실행됩니다. |
| 7. 머지      | CI(lint → format:check → build) 통과와 리뷰 승인 후 **Squash and merge**              |
| 8. 정리      | `git switch main && git pull`. 머지된 원격 브랜치는 자동으로 삭제됩니다.              |

## 이슈

| 타입                                          | 이슈 | 예시                                                      |
| --------------------------------------------- | ---- | --------------------------------------------------------- |
| `feat`, `fix`                                 | 필수 | 레시피 저장 기능, 로그인 후 튕기는 버그                   |
| `refactor` `style` `docs` `test` `chore` `ci` | 선택 | README 수정, 설정 변경. 이슈 없이 바로 PR을 올려도 됩니다 |

- 이슈는 "해야 할 일"을, PR은 "실제 코드 변경"을 담습니다.
- 큰 기능은 이슈 1개에 PR 여러 개로 나눠도 됩니다.

## 타입

브랜치, 커밋, PR 제목에 같은 타입을 씁니다.

| 타입       | 용도                                     |
| ---------- | ---------------------------------------- |
| `feat`     | 새 기능, 기존 기능 개선                  |
| `fix`      | 버그 수정                                |
| `refactor` | 동작 변화 없는 코드 개선                 |
| `style`    | 화면 스타일·마크업 변경 (로직 변화 없음) |
| `docs`     | 문서                                     |
| `test`     | 테스트                                   |
| `chore`    | 설정, 의존성, 빌드 등 기타               |
| `ci`       | GitHub Actions 등 CI 설정                |

- `feat`은 사용자가 쓸 수 있는 기능이 새로 생기거나 바뀔 때만 씁니다.
- 라이브러리 추가, 폴더 구조 변경, 라우터 설정처럼 사용자 기능이 없는 변경은 `chore` 또는 `refactor`입니다.
- 여러 타입이 섞이면 변경 비중이 가장 큰 쪽을 고릅니다. 가능하면 PR을 나눕니다.

## 브랜치

```
{타입}/{이슈번호}-{영문-설명}   # 이슈가 있을 때
{타입}/{영문-설명}              # 이슈가 없을 때 (feat·fix 제외)
```

- 예) `feat/24-recipe-save`, `fix/31-login-redirect`, `docs/update-readme`
- 설명은 영문 소문자, 단어 사이는 하이픈(`-`)

## 커밋 메시지

```
{타입}: {설명}
```

- 예) `feat: 레시피 저장 버튼 추가`, `fix: 로그인 후 이전 페이지로 이동하지 않는 문제 수정`
- 콜론 뒤에 한 칸 띄우고, 앞에는 띄우지 않습니다 (`feat : ...` ✗).
- 설명은 한국어로, 무엇을 했는지 짧게 씁니다.
- **한 줄이 기본입니다.** 본문은 이유가 코드만으로 드러나지 않을 때만, 한 줄 띄우고 "왜"를 적습니다.
- 작업 내용 정리는 커밋이 아니라 PR 본문에 씁니다.

```
fix: 레시피 목록 무한 스크롤 중복 요청 수정

스크롤 이벤트가 연속으로 들어올 때 이전 요청이 끝나기 전에
다음 페이지를 또 요청해서 같은 레시피가 두 번 보였음
```

Squash 머지라서 PR 안의 커밋은 `main`에 그대로 남지 않습니다. 그래도 리뷰하기 쉽게 같은 형식을 지켜주세요.

## PR

- **제목:** 커밋 메시지와 같은 `{타입}: {설명}` 형식. 머지하면 PR 제목이 `main`의 커밋 메시지가 됩니다.
  - 예) `feat: 레시피 저장 추가`
  - 제목에 `@coderabbitai`라고만 쓰고 PR을 열면 CodeRabbit이 변경 내용을 보고 이 형식으로 제목을 만들어줍니다.
- **본문:** PR 템플릿을 채워주세요. 연관 이슈는 `close #24`처럼 적으면 머지할 때 이슈가 닫힙니다.
- PR 하나에는 한 가지 목적만 담습니다.
